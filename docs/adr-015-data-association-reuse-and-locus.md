# ADR-015: Ассоциация данных — матрица self-attention, переиспользование точек и детерминированный локус

Дата: 2026-06-27  
Статус: **Superseded** — hard-cut на единственный алгоритм `nextgen-gravity` (phase-конструктор: ST-DBSCAN → H3-field attention → gravity join), GNN/PDAF/JPDAF selector и offline auto-tune удалены из кода. Актуальная реализация: `packages/shared/src/domain/tracking/nextgen/`.

Связано: [ADR-007](./adr-007-trajectory-graph-kalman-worker.md), [ADR-009](./adr-009-osint-pre-collapse.md), [SDD phase-1c attention-assign](./sdd/tracking/phase-1c-attention-assign.md)

---

## Контекст

Текущая ассоциация (`assignCandidates.ts`) — **жадный per-candidate GNN**: точка обрабатывается одна за другой в хронологии, берёт `argmin linkCost`, после линковки **исключается** (`consumed.add(eventLocationId)`) и в следующий трек уже не попадёт. «Авто-расширение локуса» сейчас сделано через `pauseFactor`, который **раздувает ковариацию** (Q/мягкий gate) на паузах.

Рисёрч сравнил это с вероятностными схемами:

| Подход | Суть | Применимость к нам |
|--------|------|--------------------|
| **GNN (текущий)** | argmin, точка → 1 трек, consume | работает, но теряет неоднозначность |
| **PDAF** | взвешенная сумма in-gate точек на трек, update Σβᵢ | требует P_D/λ, даёт smearing |
| **JPDAF** | совместные гипотезы, точка ≤ 1 трек | дорого, конфликты гейтов у нас редки |

**Выводы рисёрча:**

- Поток разрежённый и уже дедуплицирован ST-DBSCAN ([ADR-009](./adr-009-osint-pre-collapse.md)) → в гейте трека обычно **одна** точка, поэтому вероятностное взвешивание (PDAF/JPDAF) даёт **низкий ROI** и риск «размазывания» (smearing) + неоткалибруемые `P_D`, `λ`.
- Реальная потребность OSINT — **сохранять неоднозначность**: одно сообщение («БПЛА над городом N») может легитимно питать **несколько** правдоподобных треков, а не разрешаться в один (JPDAF делает наоборот: точка ≤ 1 трек).
- «Авто-расширение локуса» через раздувание ковариации непрозрачно и плохо предсказуемо.

---

## Решение

### 1. Флаг переиспользования точек — `reuseAcrossTracks` (матрица self-attention)

Матрица `точка × трек` становится явной: для точки `i` строка — это все треки, в локус которых она попадает (`ρ ≤ 1`, см. п.2). Меняется **только шаг consume**, формула линковки лаконична:

```text
linksᵢ = { j : ρ(i, j) ≤ 1 }                   // строка self-attention для точки i

reuse = off (дефолт, = текущее):
    assignᵢ = argmin_{j ∈ linksᵢ} ρ(i, j)
    consume(i)                                  // точка исключается из следующего шага

reuse = on:
    assignᵢ = linksᵢ                            // точка идёт во ВСЕ сходящиеся треки
    нет consume(i)                              // точка остаётся доступной
```

- **off** — поведение без изменений: точка, попавшая в трек, исключается из расчёта на следующем шаге.
- **on** — точка добавляется во все треки, где она в локусе (`ρ ≤ 1`); fan-out гипотез сохраняется.

Это **не** PDAF/JPDAF: нет взвешивания `βᵢ`, нет смешанного update. Каждый трек получает точку как обычное наблюдение; неоднозначность выражается копией точки в нескольких треках, а не дробной вероятностью.

### 2. Детерминированный локус по допуску маневра (грех-бюджет)

Это **не «упрощение predict»**, а **перенос владения локусом**. `predict` отдаёт только **вектор** прогноза `ẑ` (предсказанную позицию); сам локус и порог строим **мы** — из бюджета допустимого «греха», а не из эволюционирующей ковариации фильтра.

Было: локус = ковариационный эллипс `{ z : D_M²(z) ≤ χ² }`, где `D_M²` через `S = H·P⁻·Hᵀ + R`, а `pauseFactor` раздувает `P/Q` → gate «дышит» стохастически (им владеет фильтр).

Стало: локус = **кинематический допуск маневра**, расширяется с паузой детерминированно (через `v_max·dt`), без правки ковариации:

```text
predict(track j, dt) → ẑ_j                       // Kalman predict отдаёт только вектор
r_доп(dt) = v_max · dt + σ_pos                    // радиус допустимого маневра за паузу dt
ρ(i, j)   = dist(zᵢ, ẑ_j) / r_доп(dt)             // чистый коэф попадания («грех»), без S
допустимо ⟺ ρ(i, j) ≤ 1                            // в пределах заданной погрешности
трек j берёт min_i ρ(i, j)                         // «лучшую точку с учётом греха» ρ
```

- Ковариацию **не меняем** взвешиванием; локус — наша конструкция поверх вектора прогноза.
- `r_доп` растёт с `dt` (длиннее пауза → шире допуск), но **кинематически**, а не через инфляцию `P` (`pauseFactor` для gate выводится из употребления).
- `ρ` — прозрачный «грех» (нормированный остаток): трек забирает лучшую (минимальный `ρ`) точку среди допустимых.

### 3. Визуализация локуса — `locusDebug` (диагностический оверлей)

Галочка **визуализации** (не алгоритмический флаг): для нод треков рисует на карте сам локус `r_доп(dt)` вокруг прогноза `ẑ`, чтобы видеть его форму и **что попадает / не попадает** (`ρ ≤ 1` vs `ρ > 1`) при расчёте.

- **Геометрия:** окружность радиуса `r_доп(dt)` с центром в `ẑ` для каждой ноды (или для последней + прогноз следующего шага). При анизотропии (вдоль/поперёк курса) — эллипс.
- **Подсветка попадания:** точки-кандидаты внутри (`ρ ≤ 1`) — зелёные, вне (`ρ > 1`) — серые; опционально подпись `ρ`.
- **Слой клиентский** (`geoMapLayers.locusDebug`), как прочие debug-слои карты; не пишется в `trackingPipelineConfigSchema`.
- **Источник параметров локуса** (на выбор при реализации):
  - **A (минимум):** клиент считает `r_доп(dt)` из кинематики профиля (`v_max`) + `dt` до соседней ноды — приближение, без изменений API.
  - **B (точно):** worker сохраняет фактический локус на ноду (центр `ẑ`, радиус/оси), API отдаёт — показывает ровно то, что использовалось в расчёте.

### 4. Связь с PDAF/JPDAF и стратегия выбора алгоритма

Сейчас остаётся **GNN** (жадная ассоциация по `ρ`) как дефолт. Вероятностное взвешивание сознательно **не внедряем**: модель неоднозначности — это `reuseAcrossTracks` (fan-out копий), а не `βᵢ`. PDAF/JPDAF остаются в backlog на случай, если замеры покажут много пересечений гейтов (высокий `attentionConflicts`).

**Инвариант миграции:** переход на новый алгоритм выполняется **только через выбор алгоритма в админке**, а не заменой кода. Любой будущий алгоритм добавляется как опция, GNN остаётся доступным:

- `associationAlgorithm: "gnn" | "pdaf" | "jpdaf" | ...` (default `"gnn"`).
- Отдельная **панель настроек алгоритма** в админке: селектор алгоритма + его специфичные параметры (для PDAF/JPDAF — `P_D`, окно скана, β₀; для GNN — текущие gate-параметры).
- Общие узлы (`reuseAcrossTracks`, `ρ`-локус, `seedWeights`) применяются поверх выбранного алгоритма, где имеют смысл.
- Смена алгоритма требует rebuild (как смена любого параметра пайплайна).

### 5. Вес тока и штраф за противоток (направленный множитель)

Направленный приор поверх `ρ`: поощряем движение **по току** (фронт→тыл), штрафуем **противоток** (шаг к фронту). Мягкий **множитель**, не хард-гейт — пограничные кейсы не теряем.

```text
f = ток в точке (вектор фронт→тыл, нормированный)
s = шаг кандидата (last_node → zᵢ)
a = cos∠(s, f) ∈ [−1, 1]                         // выравнивание шага с током

ρ' = ρ · (1 + γ_против · max(0, −a))             // штраф за противоток (a<0)
        / (1 + γ_ток    · max(0, +a))            // вес тока: бонус по току (a>0)
```

- **`γ_ток`** («вес тока») — поощрение движения по потоку; **`γ_против`** («штраф за противоток») — подавление обратного тока. `a ≈ 0` (поперёк) — нейтрально.
- Решение по-прежнему `min_i ρ'` (и `ρ' ≤ 1`-критерий локуса считается по `ρ`, штраф влияет на выбор/стоимость, не на сам gate).

**Источник тока `f` = A+B (блендинг):**

- **A (база):** градиент поля `front_distance_km` (фронт→тыл) — детерминирован, без циркулярности, прямо под гипотезу.
- **B (уточнение):** эмпирическое flow-поле из агрегированных коридоров ([ADR-013](./adr-013-trajectory-flow-and-path-fan.md)) — локальные потоки.
- `f = normalize((1 − w_emp)·f_A + w_emp·f_B)`; при отсутствии прогретого `f_B` → fallback на `f_A` (`w_emp` эффективно 0).

**Связь с прочим:** ортогонально `seedWeights` (те — «где зарождать» по позиции; этот — «куда двигаться» по направлению). Хард `rear-front gate` (по скорости трека) сохраняется как отдельный предохранитель; «ток» работает и на 1-м сегменте (v≈0), т.к. `f` — глобальное поле.

### Конфиг и UI

**Принцип:** все коэффициенты штрафов/весов и пороги — **тюнятся в админке**, без хардкода в коде (домен хранит только дефолты-фолбэки). Источник правды для значений — `trackingPipelineConfigSchema` → `state_track_pipeline.config`.

Инвентарь настроек админки (`TrackingKinematicsSettingsWidget`, секции):

| Секция | Поле (config) | Назначение | Статус |
|--------|---------------|-----------|--------|
| Зарождение | `seedMin`, `seedMaxFrontDistanceKm` | порог веса seed, макс. дистанция до фронта | ✅ есть |
| Зарождение | `seedRegionFront`, `seedRegionInteriorRf`, `seedFrontProximityD0Km` | буст у фронта / штраф в тылу / затухание D0 | ✅ есть |
| Направленность | `flowWeight` (`γ_ток`) | бонус за движение по току | ⬜ ADR |
| Направленность | `counterFlowPenalty` (`γ_против`) | штраф за противоток | ⬜ ADR |
| Направленность | `flowEmpiricalBlend` (`w_emp`) | доля эмпирического тока B (default 0 = только A) | ⬜ ADR |
| Ассоциация | `reuseAcrossTracks` (галочка) | точка в один лучший трек / во все сходящиеся | ⬜ ADR |
| Ассоциация | `associationAlgorithm` (селектор) | GNN / PDAF / JPDAF / … (default `gnn`) | ⬜ ADR |
| Карта (клиент) | `geoMapLayers.locusDebug` (галочка) | оверлей локусов + in/out подсветка | ⬜ ADR |

- Алгоритм-специфичные параметры (PDAF/JPDAF: `P_D`, окно скана, β₀) появляются в панели **только** при выборе соответствующего `associationAlgorithm`.
- Проброс алгоритмических полей: `shared` (`ResolveOpts`/`BuildMatrixOpts`) → `worker` (`assignBatch` → `resolveAssignments`).
- `locusDebug` — чисто клиентский тумблер карты, в `config` не пишется.

## Не делаем

- Вероятностный update (PDAF/JPDAF), `βᵢ`-смешивание, оценку `P_D`/`λ` — backlog (внедрять только как выбираемый алгоритм, **не заменой GNN**).
- Раздувание ковариации как механизм расширения локуса (`pauseFactor` для gate выводится из употребления).
- Дедупликацию копий точки между треками при `reuse=on` — неоднозначность намеренно сохраняется.
- Изменение схлопывания ([ADR-009](./adr-009-osint-pre-collapse.md)) и хранения треков ([ADR-007](./adr-007-trajectory-graph-kalman-worker.md)).

## Последствия

| Плюс | Минус |
|------|-------|
| Сохранение неоднозначности OSINT (один сигнал → N треков) | При `reuse=on` рост числа нод и возможное дублирование сегментов |
| Прозрачный локус (`ρ` против допуска) вместо непрозрачной инфляции P | `reuse=on` требует ревизии метрик покрытия (точка считается многократно) |
| `locusDebug` даёт визуальную верификацию gate (что попало/нет) | Вариант B `locusDebug` требует хранить локус на ноду |
| Вес тока/штраф противотока душат обратный поток мягко, без потери кейсов | `γ`-параметры требуют тюнинга; flow-поле B даёт циркулярность при `w_emp>0` |
| Дёшево: без `P_D`/`λ` и enumeration гипотез | Не разрешает cross-track конфликты (это и не цель) |
| Флаг — обратимо, дефолт сохраняет текущее поведение | Два режима ассоциации в коде |

## Критерии принятия

- `reuse=off` даёт побитово текущее поведение (consume-once, argmin по `ρ`).
- `reuse=on`: точка с `ρ ≤ 1` к двум трекам попадает в оба; unit-fixture это покрывает.
- Локус: решение зависит только от `ρ = dist / r_доп(dt)`, `predict` отдаёт лишь вектор, `P` между шагами не модифицируется gate-логикой.
- Галочка в админке управляет `reuseAcrossTracks`, значение доезжает до `resolveAssignments` (проверка через rebuild).
- `locusDebug`: при включении слоя локусы нод и in/out подсветка (`ρ ≤ 1` зелёные, `ρ > 1` серые) видны на карте.
- Сейчас активен **GNN**; любой будущий алгоритм добавляется как опция селектора (`associationAlgorithm`), GNN остаётся выбираемым (не заменён).
- Вес тока/штраф противотока: при `γ_против > 0` шаг против тока (`a < 0`) получает `ρ' > ρ`; при `w_emp = 0` ток = только градиент `front_distance` (детерминирован).
